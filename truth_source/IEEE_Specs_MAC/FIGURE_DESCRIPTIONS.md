# Figures and Diagrams — Visual Descriptions

This file contains human-readable descriptions of all figures and diagrams found in the IEEE 802.3-2008 MAC clauses. These descriptions provide visual context for the figures that are rendered as vector graphics in the original PDF and cannot be extracted as text.

---

## Clause 2 — MAC Service Specification

### Figure 2-1 — Service specification primitive relationships (Page 119)
**Type:** Architecture diagram

Shows the three-layer interaction model between MAC client, Media Access Control, and PHY.

- **Top layer (MAC client):** Sends `MA_DATA.request` downward and receives `MA_DATA.indication` upward
- **Middle layer (Media Access Control):** The central processing block that handles MAC operations
- **Bottom layer (PHY):** Physical layer interface
- **Variables (left side, PHY→MAC):** `carrierSense`, `receiveDataValid`, `collisionDetect`, `transmitting` — signals flowing from PHY to MAC
- **Functions & procedures (right side, MAC→PHY):** `TransmitBit`, `ReceiveBit`, `Wait` — operations the MAC invokes on the PHY

The diagram illustrates how the MAC sublayer sits between the client and the physical medium, translating service primitives into physical signals.

## Clause 3 — MAC Frame and Packet Specifications

### Figure 3-1 — Packet format (Page 124)
**Type:** Frame structure diagram

Shows the Ethernet packet layout as a vertical stack of fields, transmitted top-to-bottom, bits left-to-right:

| Field | Size |
|-------|------|
| PREAMBLE | 7 octets |
| SFD (Start Frame Delimiter) | 1 octet |
| DESTINATION ADDRESS | 6 octets |
| SOURCE ADDRESS | 6 octets |
| LENGTH/TYPE | 2 octets |
| MAC CLIENT DATA | 46 to 1500/1504/1982 octets |
| PAD | variable |
| FRAME CHECK SEQUENCE | 4 octets |
| EXTENSION | variable (1000 Mb/s half duplex only) |

The diagram labels the entire structure as "PACKET" with the "FRAME" portion spanning from Destination Address through FCS.

### Figure 3-2 — Service primitive mappings (Page 125)
**Type:** Mapping diagram

Shows how `MA_DATA.request(destination_address, source_address, mac_service_data_unit, frame_check_sequence)` parameters map to packet fields:
- `destination_address` → DA field (solid arrow)
- `source_address` → SA field (solid arrow)
- `mac_service_data_unit` → LENGTH/TYPE and MAC CLIENT DATA fields (solid arrows)
- `frame_check_sequence` → FCS field (dashed arrow, optional)
- PAD field shown with dashed arrow (optional, generated by MAC if needed)

The bottom shows `MA_DATA.indication(destination_address, source_address, mac_service_data_unit, frame_check_sequence)` as the receive-side mapping.

### Figure 3-3 — Address field format (Page 126)
**Type:** Bit field diagram

Shows the 48-bit address field structure:
- **I/G bit** (1 bit): 0 = Individual Address, 1 = Group Address
- **U/L bit** (1 bit): 0 = Globally Administered Address, 1 = Locally Administered Address
- **46-BIT ADDRESS**: The remaining address bits

## Clause 4 — MAC (CSMA/CD)

### Figure 4-1 — Relationship among CSMA/CD procedures (Page 136)
**Type:** Architecture/procedural model diagram

Shows the static structure of the seven-process CSMA/CD procedural model, organized in three layers:

- **MAC CLIENT layer:** FrameTransmitter and FrameReceiver processes
- **MEDIA ACCESS SUBLAYER:** Contains the core procedures:
  - Transmit path: TransmitFrame → TransmitDataEncap → ComputePad → TransmitLinkMgmt → StartTransmit → BitTransmitter → PhysicalSignalEncap → TransmitBit
  - Receive path: ReceiveFrame → ReceiveDataDecap → CRC32 → LayerMgmt/RecognizeAddress → ReceiveLinkMgmt → StartReceive → BitReceiver → PhysicalSignalDecap → ReceiveBit
  - Management: Deference, BurstTimer (*), SetExtending (*)
  - Half-duplex only (†): WatchForCollision, BackOff, Random, StartJam, InterFrameSignal
- **PHYSICAL LAYER:** TransmitBit, Wait, ReceiveBit

Annotations: † = Not applicable to full duplex; * = Applicable only to half duplex at 1000 Mb/s

### Figure 4-2a — Control flow summary: TransmitFrame (Page 137)
**Type:** State/flow diagram

TransmitFrame flowchart:
1. Check Transmit ENABLE? → no: Done (transmitDisabled)
2. Assemble frame
3. Check burst continuation? (1000 Mb/s half duplex only)
4. Check deferring on? → yes: loop back
5. Start transmission
6. Check halfDuplex AND collisionDetect? → yes: send jam → increment attempts → check late collision and > 100 Mb/s? → check too many attempts? → compute backoff → wait backoff time → loop back
7. Check transmission done? → no: loop back
8. Exit states: Done (transmitOK), Done (lateCollisionErrorStatus), Done (excessiveCollisionError)

### Figure 4-2b — Control flow summary: ReceiveFrame (Page 138)
**Type:** State/flow diagram

ReceiveFrame flowchart:
1. Check Receive ENABLE? → no: Done (receiveDisabled)
2. Start receiving → loop until done receiving
3. Check frame too small? (collision) → yes: Done (receiveDisabled)
4. Check recognize address? → no: Done (receiveDisabled)
5. Check frame too long? → yes: Done (frameTooLong)
6. Check valid frame check sequence? → no: check extra bits? → Done (alignmentError or frameCheckError)
7. Check valid length/type field? → no: Done (lengthError)
8. Disassemble frame → Done (receiveOK)

### Figure 4-3a — Control flow: MAC sublayer (Page 139)
**Type:** State/flow diagram

Two parallel process flows:

**BitReceiver process (left):**
- Wait for receiving started → receive a bit
- Check # of bits ≥ slotTime? → yes: extending off (1000 Mb/s half duplex)
- Check errors in extension? → yes: extensionOK off
- Check receiveDataValid off or frameFinished on?
- Check extending off? → yes: receiving done; no: receiveSucceeding off → receiving done

**BitTransmitter process (right):**
- Wait for transmission started → transmit a bit
- Check end of frame? → no: loop back
- Check bursting on? → yes: fill interframe → check frameWaiting and bursting on? → loop or bursting off
- Transmission done

### Figure 4-3b — Control flow: MAC sublayer (Page 140)
**Type:** State/flow diagram

Three parallel process flows:

**Deference process (left):**
- Check channel busy? → yes: deferring on → check channel free? → yes: wait interpacket gap → deferring off → check frameWaiting? → loop

**BurstTimer process (right, 1000 Mb/s half duplex):**
- Check bursting on? → yes: clear burstCounter → wait one Bit Time → increment burstCounter → check bursting on and burstCounter < burstLimit? → loop or bursting off

**SetExtending process (bottom, 1000 Mb/s half duplex):**
- Check receiveDataValid on? → yes: loop
- Check halfDuplex and > 100 Mb/s? → yes: extending on

### Figure 4-4 — Packet bursting (Page 142)
**Type:** Timing diagram

Shows a burst transmission sequence at 1000 Mb/s half duplex:
```
[MAC Packet with Extension] [InterPacket] [MAC Packet] [InterPacket] ... [MAC Packet]
|←—————————— burstLimit ——————————→|
|←—————————— duration of carrier Event ————————————————→|
```

The first packet includes carrier extension. Subsequent packets are separated by interpacket fill (extension bits), maintaining carrier detection. The entire burst must not exceed burstLimit.

### Figure 4-5 — Frame with carrier extension (Page 143)
**Type:** Frame structure/timing diagram

Shows a frame with carrier extension at 1000 Mb/s half duplex:
```
[Preamble][SFD][DA][SA][Length/Type][Data/Pad][FCS][Extension]
|←———————— minFrameSize —————————→|
|←———————————————— slotTime ————————————————————————→|
|←———————————— FCS Coverage —————————————→|
|←———————— late collision threshold (slotTime) ————————→|
|←———————————— duration of carrier event ——————————————→|
```

Extension bits are appended after FCS to ensure the transmission duration meets slotTime requirements.

## Clause 31 — MAC Control

### Figure 31-1 — Architectural positioning of MAC Control sublayer (Page 421)
**Type:** Architecture/layering diagram

Shows the OSI Reference Model layers mapped to LAN CSMA/CD layers:
- **OSI layers:** Application, Presentation, Session, Transport, Network, Data Link, Physical
- **LAN CSMA/CD layers:** Higher Layers → LLC (Logical Link Control) or other MAC Client → **MAC CONTROL (OPTIONAL)** → MAC — Media Access Control → Physical Layer

The MAC Control sublayer is positioned as an optional layer between the MAC client (LLC) and the MAC sublayer.

### Figure 31-2 — MAC Control sublayer support of interlayer service interfaces (Page 422)
**Type:** Interface diagram

Shows the MAC Control sublayer sitting between MAC client and MAC:
- **MAC client ↔ MAC Control:** `MCF:MA_DATA.request` (down), `MCF:MA_DATA.indication` (up), `MA_CONTROL.request` (down), `MA_CONTROL.indication` (up)
- **MAC Control ↔ MAC:** `MAC:MA_DATA.request` (down), `MAC:MA_DATA.indication` (up)

Legend: MCF = interface to MAC client; MAC = interface to subordinate sublayer

### Figure 31-3 — MAC Control frame format (Page 425)
**Type:** Frame structure diagram

Shows the MAC Control frame layout, transmitted top-to-bottom, bits left-to-right:

| Field | Size |
|-------|------|
| DESTINATION ADDRESS | 6 octets |
| SOURCE ADDRESS | 6 octets |
| LENGTH/TYPE | 2 octets (value: 88-08) |
| MAC CONTROL OPCODE | 2 octets |
| MAC CONTROL PARAMETERS | (minFrameSize - 160) / 8 octets |
| RESERVED (transmitted as zeros) | variable |

### Figure 31-4 — Generic MAC Control Receive state diagram (Page 429)
**Type:** State diagram (STATE DIAGRAM)

Shows the MAC Control receive state machine with four states:

1. **BEGIN** → `receiveEnabled = FALSE`
2. **WAIT FOR RX:** Waits for `MAC:MA_DATA.indication(DA, SA, mac_service_data_unit, fcs, reception_status)`
3. **CHECK TYPE:** Checks if `lengthOrType = 802.3_MAC_Control`
   - If NO → **PASS TO CLIENT:** Generate `MCF:MA_DATA.indication(DA, SA, mac_service_data_unit, fcs, reception_status)` → back to WAIT FOR RX
   - If YES → **CHECK OPCODE:** Parse `opcode = data[1:16]`
4. **CHECK OPCODE:**
   - If `opcode = {supported code}` → **INITIATE MAC CONTROL FUNCTION:** Perform opcode-specific operation → back to WAIT FOR RX
   - If `opcode ≠ {supported code}` → **UCT** (Unsupported Control Type) → back to WAIT FOR RX

Note: The opcode-specific operation is launched as a parallel process, not synchronously.
